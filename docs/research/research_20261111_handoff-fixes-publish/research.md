# Research: Handoff, fixes, and foundry publish

**Date:** 2026-11-11

## Purpose

The three questions behind `milestone_v2026.11.11_handoff-fixes-publish`: why the project's release tags carry no GitHub Release, and what stands in the way of Foundry creating one; how a milestone's work passes from one session to the next when it runs across many; where a release that closes no milestone keeps its record.

## Conclusion

- **GitHub Releases.** A git tag and a GitHub Release are separate objects: pushing a tag creates no Release, which is made on an existing tag by the web interface, `gh release create`, or the REST API. Vork's four Releases, `v2026.10.13` to `v2026.10.18`, were made by hand under the Vork account; `v2026.10.23` and `v2026.10.24` carry tags alone, because neither the convention nor the release skill names the act. Nothing blocks Foundry from it: the Vork account holds `push` on the repository, which covers tags and Releases; both rulesets target branches, so a tag push passes; Foundry already carries Octokit and reads a clone's origin. Settled in design: the target resolves from the release record on `origin/main`, never from main's tip alone, and the act converges on a re-run; the command is `publish`, since a rollout in the convention's vocabulary is Deployment's; the Release's name comes from the record's heading, which gains a title, as the existing tags' subjects already do (`v2026.10.24 — identity per actor; the vault's readers and apps`); Foundry runs only where a Vork clone is installed, so the release skill keeps the by-hand form beside it.
- **Handoff.** A session's working context ends with it, and its transcript stays on the machine that produced it; `decomposition.md`'s Current orients a fresh session to the milestone, and nothing records where the last session stopped. The handoff record holds that: one file per milestone or fix, an entry per session, newest on top, each complete on its own, its session id and transcript path the way a later session finds a past one. A Brief rewritten in place at each wrap-up was considered and set aside at the preview: session 2's rewrite would drop session 1's notes and any open item it failed to carry from view, git history being no place a session reads at startup; separate files per session keep the same history at the cost of a folder to scan for the newest. Wrapping up automatically at a context threshold was examined and dropped by the Principal's ruling: the model receives no signal of its own context fill (Claude Code gives `context_window.used_percentage` to the status line alone, and no hook input carries usage), so it would take a hook per harness; the Principal calls the wrap-up instead. An entry rides a lane, so the next session finds the newest with `git log --all --source -1 --format=%S -- <record-folder>/handoff.md`, which names the branch holding it (checked on this repository, 2026-11-11).
- **Fixes.** Three of Vork's releases closed no milestone: `v2026.10.18`, the lockfile hotfix (#28), and `v2026.10.23` and `v2026.10.24`, convention changes landed from the backlog on `fix/backlog/*` lanes. Their records read "Milestone: none", and the convention gave the latter two neither a home nor a lane. Ruling 2026-11-11: both kinds are one, a fix — an immediate bug fix, or a change too small to open a milestone — recorded under `docs/fixes/`, riding `fix/<fix-folder>/<slug>` off `main`, synced to `dev` on `fix/<fix-folder>/sync`; a milestone's own fix lanes stay `fix/<milestone-folder>/<slug>` off `dev`, and the word "hotfix" leaves the convention. At the preview a fix gained a second base: one that needs no release of its own rides `dev` to the next release, as this release's adoption in every existing project does; a fix lane off `main` then reads its templates from `dev`, where a template change lands first.
